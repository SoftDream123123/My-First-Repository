### 5.3 本轮发现并修复的测试缺陷（偶发失败）

最终验证阶段，一次全量运行出现 **1 failed / 458 passed**。定位后确认这是**既有的测试竞态**，
不是产品缺陷，也不是本轮新增的用例：

| 项 | 内容 |
|---|---|
| 位置 | `test_evaluation_stream.py::TestTrigger::test_idempotent_when_running` |
| 现象 | `assert stream.get_run(interview_id) is run_before` 偶发失败（实测约 1/11 次全量运行） |
| 引入时间 | `b32f952 feat(evaluation)`，早于本次工作 |

**根因**：该用例用 `SlowProvider`（每个方法 `sleep(0.15)`）拖慢评估来「制造」运行中的观察窗口，
整轮评估约 1.5 秒。若第二次 `POST /evaluate` 到达前后台运行已经跑完（机器负载、GC、线程调度延迟），
`stream.start_run` 会先 `remove_run` 再创建**新的** `EvaluationRun` 对象，于是「对象同一性」断言失败。

用独立探针复现了该机制，确认这是**必然**而非巧合：

```
首次 start_run 返回对象: 2115291937968
首个 run 终态: failed
再次 start_run 返回对象: 2115296668048
=> 断言 `get_run(id) is run_before` 会失败: True
```

**修复**：把「时间赌注」换成**事件闸门**。`GatedProvider` 在第一次 `evaluate_answer` 上阻塞，
测试主动 `gate.set()` 才放行 —— 不放行则运行必然停在 `RUNNING`，断言完全确定。
`finally` 中放行并留 10 秒兜底，断言失败时也不会让后台线程悬停。

**验证**：削弱性变异仍被捕获 —— 把路由中的幂等守卫改成 `if False:`，该用例立刻失败在
`get_run(...) is run_before`，证明修复没有把断言改松：

```
FAILED TEST: tests.test_evaluation_stream.TestTrigger :: test_idempotent_when_running
E   AssertionError: assert EvaluationRun(interview_id=1, ...) is EvaluationRun(interview_id=1, ...)
```

> 结论：**测试套件本身的一处既有缺陷已修复**。同一次压测还暴露出一个**产品侧**竞态，见 §5.4。

### 5.4 本轮发现并修复的产品缺陷（SSE 流静默截断）

这是本次测试发现的**唯一真实产品缺陷**，由新增的端到端流程用例捕获。

| 项 | 内容 |
|---|---|
| 位置 | `app/evaluation/stream.py` → `stream_events()`（代码来自 `b32f952`，本轮之前从未被改动） |
| 发现方式 | 12 轮全量重复运行中出现 1 次失败：`test_e2e_flows.py::TestFlow3StreamingEvaluation::test_evaluate_stream_report_reevaluate` 收到的 SSE 事件序列缺少 `done` |
| 性质 | **产品竞态**（非测试问题），已确定性复现 |
| 违反的契约 | module-06 §5.5「`done` 与 `error` 互斥且**必有其一**」、PRD §7 |

**根因**：读取方与写入方各自分两步，两个窗口叠加：

```python
# 读取方（旧）
for name, payload in run.snapshot():        # ① 先 materialize 一份快照
    yield format_event(name, payload)
if run.status in (RUN_DONE, RUN_FAILED):    # ② 再单独读状态
    return

# 写入方（旧）
run.status = RUN_DONE                       # ③ 先置状态
publish(run, "done", {...})                 # ④ 再推终结事件
```

只要 ③④ 落在 ①② 之间，生成器就会在 ② 处 `return`，而它已重放的快照里**永远不会有 `done`**；
更糟的是此刻订阅尚未建立，`done` 也投递不到任何人。客户端因此收到一段**没有终结事件的流并静默关闭** ——
前端表现为评估停在半截，既不报错，也不出现「连接已断开 / 重新连接」提示。

同类窗口还有第二处：第 ① 步与「订阅」之间 publish 的所有事件会被**直接丢弃**（客户端看到跳号）。

**确定性复现**（修复前）：

```
已重放: event: question | data: {"seq": 1, "score": 7.0}
后续产出: []
客户端是否收到终结事件: False
```

**修复**：把「订阅 + 取快照 + 读状态」收进**同一把锁**，并新增 `publish_terminal()`
让「写入终结事件」与「置运行状态」原子完成：

```python
with run.lock:
    replayed = list(run.events)                 # 与订阅同临界区
    finished = run.status in (RUN_DONE, RUN_FAILED)
    if not finished:
        run.subscribers.append(subscriber)
```

正确性：终结写入若发生在取锁**之前** → `finished=True` 且终结事件必在 `replayed` 中；
若发生在**之后** → 我方已在订阅者名单内，终结事件经队列送达。**两个方向都不丢**，
且第 ① 步与订阅之间的事件丢弃窗口同时被消除。

**回归测试**（`TestReplayWindow`，2 条）：
- `test_terminal_event_survives_completion_landing_mid_replay` —— 显式构造该交错，断言流仍以 `done` 收尾
- `test_events_published_after_replay_are_delivered_exactly_once` —— 断言重放与队列不重叠、终结事件恰好一次

两条用例在修复前**均失败**（RED，第二条还暴露出事件被整体丢弃），修复后**均通过**（GREEN）。
用例采用有界读取 + 毫秒级心跳，流若被截断会**快速失败而不是挂住**。

**验证**：修复后连续 **15 轮全量运行全绿**（修复前该竞态约 1/12 概率命中）。

**顺带清理**：`EvaluationRun.snapshot()` 因修复而不再被引用，已删除 —— 新写法必须在与状态读取
同一临界区内取列表，而 `snapshot()` 自身会取锁，非重入锁下会死锁。

### §5.4 架构约束已自动化

- `service.py` 不出现 `db.execute` / `session.execute`（不直接写 SQL）

### 一处设计取舍需留意

`GET /api/interviews/{id}/report` 的 `evaluated_at` 取自 `report.updated_at`。若重新评估时 `updated_at` 与上次写入落在**同一秒**内，`test_reevaluate_updates_report` 断言的 `>= created_at` 仍成立，但时间戳不会变化。这是 `DECIMAL`/`DATETIME` 精度层面的已知边界，不影响正确性。

## 八、结论

- `/api` 下 **26 个 method-route 全部有 HTTP 层用例**，**461 条用例全绿**，覆盖鉴权、参数校验、业务规则、状态机、错误码、数据隔离与响应脱敏。
- 计划书 module-08 §4 的三条核心流程与 §4.4 异常路径**全部有对应用例**；§5.1–§5.4 的非功能验收项除 §七 列出的 7 项外均已自动化。
- 本轮新增 117 条用例，其中 **8 个变异全部被捕获**，可确认新用例测量的是真实行为而非空转。
- **发现并修复 1 个真实产品缺陷**：`stream_events` 的重放窗口竞态会让 SSE 流**静默截断**（既无 `done` 也无 `error`，前端停在半截且无提示），违反 module-06 §5.5「done/error 必有其一」。处理过程为：确定性复现 → 加 2 条回归测试（RED，均失败）→ 修复（GREEN）→ 15 轮全量压测全绿（§5.4）。
- 产品代码改动仅限 `app/evaluation/stream.py` 一个文件；其余全部为测试与文档新增。
- **发现并修复 1 处既有测试竞态**：`test_idempotent_when_running` 用 `sleep` 赌时间窗口（约 1/11 概率失败），改为事件闸门同步；削弱性变异仍被捕获，证明断言未被改松（§5.3）。
- 测试可完全离线运行，不需要网络与 API Key，满足交付物的开箱可验证要求。
