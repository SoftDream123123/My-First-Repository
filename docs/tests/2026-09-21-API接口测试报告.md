## 二、运行方式与环境

```bash
cd backend
python -m pytest tests/api -q          # 只跑本轮新增的接口套件
python -m pytest                       # 全量（1419 条）
```

| 环境项 | 取值 |
|---|---|
| 数据库 | MySQL，独立测试库 `interview_test`（与开发库物理隔离） |
| 测试库建法 | `drop_all` + `create_all` 从**模型**重建（不跑 alembic） |
| AI Provider | `PROVIDER_NAME=mock`；需要精确控制 AI 行为的用例用 `monkeypatch` 注入假 Provider |
| bcrypt 代价因子 | 4（生产 12，仅为测试提速） |
| 用例隔离 | 每个用例前 `TRUNCATE` 全部业务表；另重置刷题的**进程内限流窗口** |
| 时间处理 | 需要时间顺序的用例一律用 **SQL 回退时间戳**，不 `sleep`（见 §6.3） |

> 测试**完全可离线运行**，不依赖网络与 API Key。

### 错误码收敛验证

统一响应体 `{code, message, detail}`；**每个模块都抽一条真实错误路径**逐条断言信封**恰好**三字段
（`test_error_envelope_is_uniform_across_all_modules`，17 条路径覆盖 9 个模块）。

| code | HTTP | 本轮验证到的场景 |
|---|---|---|
| `VALIDATION_ERROR` | 400 | 字段越界、枚举非法、维度不属岗位、路径参数类型错（`/interviews/abc/complete`） |
| `UNAUTHORIZED` | 401 | 缺 token、密码错、账号禁用、**候选人凭码激活时未登录** |
| `INVALID_TOKEN` | 401 | **过期**（新补）、**换密钥签发**（新补）、载荷篡改 |
| `FORBIDDEN` | 403 | 跨用户访问、角色不符（**双向**：HR→候选人端点、候选人→HR 端点、admin→候选人端点） |
| `NOT_FOUND` | 404 | 资源不存在、题目不属该面试、**未关联简历（而非 403）** |
| `BUSINESS_ERROR` | 409 | 状态机非法迁移（`detail={from,to}`）、重名、被引用不可删、取不到题、限流、重复接受邀请 |
| `INTERNAL_ERROR` | 500 | 未预期异常（**响应体不含堆栈或异常原文**） |
| `AI_PROVIDER_ERROR` | 502 | 出题 / 补题 / 准备提纲 / 参考答案生成 / 候选人反馈 |
| `VALIDATION_ERROR` | **422** | **仅一处**：简历正文超过 20000 字符 |

> ⚠️ **两处不属于本信封**（本轮新发现，已修正 `docs/apis/API接口文档.md` §2.3）：
> **路径不存在**的 404 与方法不对的 405 由 Starlette 在路由层直接返回
> `{"detail": "Not Found"}` / `{"detail": "Method Not Allowed"}`，**没有 `code` 字段**。
> 两者都只由前端笔误触发，但**统一错误拦截器必须容忍 body 里没有 `code`**。

### 6.1 为什么需要这一步

**「刚写完就通过」的测试证明不了任何事** —— 它可能什么都没断言。
因此每个模块写完后，都往**生产代码**里植入一个应当被捕获的缺陷，跑对应用例，
**用例必须失败**；每次变异后立即还原文件并校验工作区干净。

### 6.3 过程中两处「用例本身不合格」的返工

这两处值得单独记下来 —— 它们说明**「用例是绿的」与「用例在测东西」是两件事**。

**（一）第 11 个变异第一次是「无效变异」，不是用例太弱。**

我先把 `question_type` 的 schema 默认值从 `None` 改成 `"short_answer"`，期望
`test_update_question_keeps_mvp2_fields_when_omitted` 变红 —— 结果它**依然是绿的**。
我没有直接判定「用例太弱」，而是先去读实现，发现守卫用的是 Pydantic 的
`model_fields_set`（「是否**显式**传了该字段」），**加一个 schema 默认值根本不改变行为**。
换成真正翻转行为的变异（`question_type = data.question_type or "short_answer"`）后，用例立刻变红。

> 教训：变异**没被捕获**时，先确认这个变异是否真的改变了行为；无效变异会给出假阴性。

**（二）第 18 个变异第一次揭示出我的**断言是恒真的**。**

幂等用例最初断言「两次补题返回的 `interview_question_id` 集合不相交」——
但每次追加都会生成**新的**面试题行、拿到**新的** id，两个集合**永远**不相交，
断言恒真，等于没测。改用「同一道**题库题**不得出现两次」：按题干内容判重，
并加一条数据库层的 `行数 == 去重后的 question_id 数` 兜底。改完后同一个变异立刻被捕获。

> 教训：断言要用**业务上唯一**的标识；用「每次调用都会变的 id」做去重判定必然恒真。

### 6.4 时间类用例一律不 `sleep`

需要「A 早于 B」的用例（简历列表按 `updated_at` 降序、编辑后冒到最前）都先用 SQL
把时间戳回退到过去，再断言顺序。原因是 `DATETIME` **只精确到秒**：同一秒内创建的两行
排序会退到 `id desc` 兜底，靠 sleep 制造的「时间差」既不必要也让用例变慢、变脆。

> 其中 `test_list_resumes_updated_order_changes_after_edit` 的第一版就是
> **碰巧通过**的：它没回退时间戳，靠 `id desc` 兜底恰好得到期望顺序，
> 完全没有验证 `updated_at` 的作用。发现后已改为回退时间戳并加前置断言。
