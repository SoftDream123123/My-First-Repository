# 01_封面

各位好，这次汇报的主题是 AI 智能面试助手的技术解构。它是一个跑在单机上的 Web 应用，用 AI 辅助真人面试官完成面试全流程，同时让候选人自己完成录简历、在线作答、刷题练习和查看反馈。接下来的四十分钟左右，我会分五个部分展开：项目概述与背景、业务流程、技术栈、六个核心模块的源码级讲解，最后是工程收获与展望。第四部分是重点，每个模块我都会讲清楚它当时遇上了什么问题，以及为什么最后那样设计。

---

# 02_目录

先看整体结构。全场分五个部分：第一部分是项目概述与背景，回答它解决什么问题、从哪来、边界画在哪；第二部分是业务流程，包含两条主线和一条把两端缝起来的简历驱动链路，还有两个状态机；第三部分是技术栈，讲选型、分层、模块边界和数据模型；第四部分是最核心的，六个模块的源码级讲解，每个模块都是固定三段式，实现、序列图、问题与解决；第五部分是工程收获、已知局限和下一步规划。

# 03_章节页_项目概述与背景

我们从第一部分开始：项目概述与背景。这部分要回答三个问题——这个产品解决什么问题、它是怎么一步步长成现在这样的、以及哪些能力是刻意不做的。最后一条往往比前两条更能说明一个项目的成熟度，因为它划出了设计者主动放弃的边界。

# 04_产品定位与解决的问题

一句话概括定位：这是一个单机部署的双端 Web 应用，AI 辅助真人面试官完成「出题、记录、评估、报告」这个闭环。系统里有三类角色，admin 负责系统管理，是唯一能建账号的角色；hr 是日常使用者，不能自助注册，只能由 admin 创建；candidate 是终端用户，凭邀请码激活。它解决的痛点在表格左边这一列，一共五条，右边是对应的应对方式。最值得一提的是最后一条：候选人无题可练，而题库资产本身是闲置的。我们的做法是复用同一套题库做刷题闭环，于是同一份简历同时驱动了 HR 侧的补题和候选人侧的推荐。

---

# 05_三条业务闭环

这一页把系统拆成三条闭环来看。左边是 HR 闭环，从建岗位开始，到读报告、导出文档结束，一共六步。中间是候选人闭环，从拿到邀请码开始，到读脱敏反馈结束。右边这条是简历驱动链路，它就是把前两条缝起来的那条线。请注意每一条步骤下面标注的发起方：第三步和第四步是候选人发起的，其余都是 HR 发起的，这个归属关系在后面的架构里会被反复引用。右下角这句话是整页的结论——简历由候选人单侧提交，却被两个方向消费：HR 侧用它来补题，候选人侧用它来推荐刷题。

# 06_版本演进

看一下它是怎么长出来的，一共五个版本。第一个版本只做 HR 侧，六个模块一次到位，配了四百六十一条用例验证。第二个版本加入候选人侧，为此新增了 candidate 角色，顺势带来了作答邀请、在线作答、脱敏反馈和一个新模块 practice。第三个版本做简历驱动与导出，新增 resume 模块，同时引入了一个新依赖 python-docx。第四个版本做简历上传解析与简历评估，新增两个依赖，加了 evaluate_resume 这个 AI 能力，但注意那句话——它没有改动任何表结构。第五个版本是最新的，做手机验证码登录，新增了 sms 这个包，并且时隔三个版本第一次动了表结构：加了一张表和一个列。值得说的是它同样没有引入新依赖——短信通道用的是和 AI 一样的抽象方式，先只实现 Mock，所以整个演示链路还是不需要任何外部账号。贯穿这五个版本的约束在底部：技术栈全程没变过，一直没有引入新框架，也没有引入任何中间件。

---

# 07_刻意画出的边界

这一页列的是刻意不做的事，六条。第一条，不保留候选人上传的简历原文件，上传只取文字、不落盘，要留原件请本地自存。第二条，后端不生成 PDF，PDF 由浏览器打印生成，代价是不支持脱离浏览器的后台批量导出。第三条，不向候选人下发逐题分和雷达图，默认只给结论、优点、待改进，是否放开总分由配置项决定。第四条，不做邮件和站内通知，邀请码在系统内展示与复制，由 HR 自行转达。第五条，流式出题不做，只有评估环节走流式。第六条，不支持多 worker 部署，因为有两个关键状态在进程内，所以启动时的 workers 参数必须是 1。这六条每一条都在下面写了允许的替代方案，边界清晰，而不是能力缺失。

# 08_章节页_业务流程

第二部分讲业务流程。这部分要回答的是「它跑起来是什么样」：两条主线、一条缝合线、两个状态机。前面几页讲的是用户视角的操作序列，最后一页会把这些操作背后的状态约束摊开——那条才是真正约束系统行为的东西。

---

# 09_HR主线

HR 主线一共七步，从建岗位到评估导出。建岗位时定义名称、JD 和评估维度，三个字段都会影响后面出题。新建面试这一步会同步出题，从题库抽五道、由 AI 按 JD 补三道，合起来恒为八道。中间两步——准备提纲和发邀请码——都是可选的。然后是逐题录入回答、标记完成，最后触发流式评估并导出。底部三条是最容易踩的地方。第一条，出题之后不能换题也不能删题，按简历补题是唯一的加题例外，而且只追加。第二条，发邀请码只在进行中的面试可行，已经完成的面试会提前拦截并返回冲突状态。第三条，重新评估失败时会退回已评估状态，旧报告不会丢，回退目标取决于库里有没有旧报告。

---

# 10_候选人主线

候选人主线是六步。第一步拿到邀请码，由 HR 自行转达。第二步打开激活页，这里关键的一点是——激活是一个公开端点，不需要先登录。第三步凭码激活并绑定到本场面试，同时创建 candidate 账号。第四步录入简历，可以粘贴，也可以上传文档由系统解析成文字。第五步关联到本场面试，注意这一步是候选人发起的。第六步逐题作答，实时保存，然后交卷，交卷是幂等的。最后等 HR 收口完成后，读脱敏反馈。下面两条是这一页最关键的取舍。左边这条：候选人作答不进入面试状态机，交卷只锁定候选人通道，面试是否完成仍然由 HR 决定；好处是 HR 可以继续补题、修订回答，不会被候选人的交卷卡住。右边这条讲账号复用规则：用户名如果已被候选人占用，必须密码一致才能复用；密码不符返回未授权；被禁用的账号一律不得复用绑定，因为绑定会消耗掉一次性邀请码，导致候选人永远打不开这场面试。

---

# 11_简历驱动链路

这条链路是六个阶段，它把 HR 侧和候选人侧缝在一起。前两个阶段由 HR 发起，第三、第四阶段由候选人发起，第五阶段开始回到 HR。中间这块标注了两处关键调用。第一处，候选人把简历关联到本场面试，这是一个候选人侧的写操作。第二处，HR 按简历补题，这是一个 HR 侧的读加写操作。下面三条是核心事实。第一，简历由候选人单侧提交，而且它出现在面试创建之后，所以关联这个动作也只能由候选人发起。第二，这是 HR 能看到候选人简历的唯一通路。第三，同一份简历可以被多场面试和多次练习复用，因为刷题推荐读的是同一张表。

---

# 12_两个状态机

这一页是两个状态机，它们是整个后端行为的真正约束。上面是面试状态机，五个状态，从草稿开始，经过进行中、已完成、评估中，到已评估。红色的虚线是失败回退：评估中断后，如果库里没有旧报告就退回已完成，如果有旧报告就退回已评估，这样已经生成过的报告不会因为一次重评失败而丢掉。蓝色的虚线是正常回退，允许从已完成或已评估退回进行中，也允许从已评估退回评估中，这条支撑了「重新评估」。下面是作答邀请状态机，四个状态，与面试状态机完全解耦。特别注意两个设计：已过期这个状态是在读取时派生的，不落库，由过期时间和当前时刻比较得出；还有一条从已接受指向已撤销的边，它是有意允许的，而且是切断候选人访问的唯一手段。右侧这张表列出了所有合法迁移，没有列出的组合一律返回冲突状态，并且在错误详情里带上原始状态和目标状态，方便定位。

# 13_章节页_技术栈

第三部分讲技术栈。这部分分五页：技术栈总览、后端严格分层、十个模块与依赖方向、数据模型，以及工程规模。我想提前说明一句：这部分不只是在罗列工具，重点在于这些选型之间怎么彼此咬合，以及哪些约束是被测试钉住的、而不是靠人记住的。

# 14_技术栈总览

技术栈一共八项，我按四类说。前三项是底座：后端用 Python 三点一一以上，本机是在三点一三上验证的；Web 框架用 FastAPI，它只做纯 JSON 接口，不渲染页面；数据库用 MySQL 八点零以上，因为要用到 JSON 列和枚举类型，整个系统只有这一个库、十六张表，也没有引入迁移框架——表结构由建表脚本和模型两处对齐。第四项是前端：原生 HTML、CSS 和 JavaScript，用 Vite 构建，没有 UI 框架、没有图表库、也没有状态管理库。往下四项是结构。架构上前后端分离，开发期经 Vite 代理，演示期由后端托管前端产物，因为同源部署，所以整个项目没有一行跨域配置。分层上是严格的三层单向依赖，这条由测试直接断言。能力层做了抽象接口：AI 可以在 Mock 和真实实现之间切换，短信通道用了同一套写法、目前只有 Mock 实现，两者都做到没有外部账号也能完整演示、完整跑通测试。部署是单机同源，必须单进程运行，因为有两个关键状态在进程内。

---

# 15_后端严格分层

这一页是后端的分层，四层。第一层 router，负责 HTTP 端点，做参数校验、角色守卫和统一响应包装，它不做数据访问。第二层 service，负责业务逻辑，做流程编排、事务边界、以及调用 AI 能力，它不直接执行 SQL。第三层 repository，负责数据访问，整个后端只有这一层执行查询。第四层是 ai 包，它是横跨三层之外的独立基础设施，只接收原始值，被 interview、evaluation 和 practice 调用。右边这一栏是测试钉住的禁止项，五条。router 不得引用 repository；repository 不得依赖上层；service 里不得出现数据库执行语句；ai 不依赖任何业务模块；core 对业务模块只做函数体内延迟导入。这五条不是写在文档里的约定，而是测试里的断言——写在文档里的约束会随时间腐化，写成测试的不会。

---

# 16_模块依赖图

这一页是十个模块的依赖方向。请先注意读图的方式：箭头表示「依赖于」，方向向下，所以越往下越是基础。最上面是 evaluation，它读取 interview 的回答来生成报告。中间是 interview 和 practice 两条业务线。再往下是三个资源模块：岗位、题库、简历。第四层是 auth，所有业务模块都依赖它做鉴权和数据隔离；短信验证码登录也落在它里面。最底下是两块基础设施：core，以及合在一块的 ai 和 sms——这两个包结构完全同构，都是「可切换的能力提供方」，都不反向依赖任何业务模块，所以画在一起。这一页真正的重点在两条红线。第一条从 practice 指向 interview，第二条从 resume 指向 interview，它们都是被架构测试明确禁止的反向边。为什么禁止？如果 practice 依赖 interview，刷题和真实面试就不再解耦；如果 resume 反向依赖任何业务模块，就会把 practice 和 interview 之间的循环依赖引进来。简历只被写入和读取，从不反向调用任何业务模块——这条约束保证了简历表是一张干净的被依赖方，能被两条业务线同时安全复用。这里补一句：新增 sms 包的时候，我们给架构测试也补了同样一条断言，保证它和 ai 一样不会反向依赖业务模块——新包不会因为没人管而长出反向边。

# 17_数据模型

数据模型一共十六张表，左边这张表按模块分组列了出来。我想重点讲三个设计决定。第一个是快照字段，右边第一栏列了五个，它们共同保证一件事：题库被修改或删除之后，历史面试记录里的题目内容不会变。第二个决定是关于候选人反馈表的。我们没有在报告表上加几列，而是把候选人反馈独立成一张表。原因是两份文本的受众和可见性规则完全不同：HR 的报告包含去留判断，候选人的反馈不含。独立成表让可见性边界落在表这一层——HR 的报告接口在结构上就读不到候选人字段，而不是靠前端不渲染来兜底。第三个决定是两处刻意缺失：报告表不设更新时间字段，因为重新评估就是整行重建；也不存总分，因为改档位不需要重新生成反馈。另外请留意标橙的两行。上面那行是用户表新加的 phone 列，它是可空且唯一的——可空是因为绝大多数账号没有手机号，唯一是因为一个号只能绑一个账号；数据库的唯一索引刚好允许多个空值，所以这两个要求可以同时满足，不需要额外机制。下面那行是新增的验证码表，它存的是一个哈希值而不是验证码本身，而且是一次性的——用完或者超时就作废。这张表还有一个特点：它不做后台清理，过期与否是在查询的时候现算的，所以我们没有为它引入任何定时任务。

# 18_工程规模

最后看一下工程规模，四个数字。第一，后端测试一千六百零一项，全部走 Mock 实现，不依赖网络。第二，四十八条接口路径，展开成六十四个方法路由。第三，十六张数据表，十个包。第四，一百二十八项端到端冒烟断言，它们是对真实运行中的服务跑通全链路的，不是单元测试。下面三张卡片是补充。前端另有一百四十五项 Vitest 单测，还有八个浏览器端的 Mock 联调台，合计七百多条断言。第三个数字是变异检查，做了三十三次——所谓变异检查，是把缺陷重新植回代码里，然后看断言是否会失败；如果断言仍然通过，说明那条测试其实没有测到东西。这三十三次里抓出了五个真 bug 和六处原型与真实契约的偏差。底部这句话很重要：整套测试不需要网络、不需要任何 API Key，检出代码就能完整跑通。

# 19_章节页_核心模块

现在进入第四部分，也是这次汇报的重点：六个模块的技术讲解。顺序是 ai 的能力抽象、interview 的出题组装、evaluation 的流式评估、interview 的邀请并发、resume 的上传解析，最后是 auth 的权限守卫。每个模块都按固定三段式展开：先看源码级的实现要点，再看一张对象交互序列图，最后讲一个真实遇到过的问题以及它的解法。这一段想传达的不只是「做了什么」，更重要的是「为什么必须这么做」。

# 20_模块01_ai_Provider抽象

第一个模块是 ai 的能力抽象。左边是真实的源码，这是一个抽象基类，定义了十个抽象方法，覆盖三条业务线：HR 侧是出题、逐题评分、多维评分、汇总报告四个；候选人侧是补参考答案、刷题判分、脱敏反馈三个；简历驱动侧是按简历匹配题目、生成准备提纲、简历匹配度评估三个。这一页最重要的一条设计约束在代码的注释里：全部方法只接收原始值，不接收任何 ORM 对象。这条约束带来两个收益：第一，ai 包不依赖任何业务模块，守住了依赖单向；第二，Mock 实现可以在完全不起数据库的情况下被单测。右边第三块讲工厂：按配置返回实现并缓存单例，而且在启动期做配置校验，配置有误就直接启动失败，而不是等第一次调用 AI 才报错。底部三列是这十个方法的分组清单。

---

# 21_模块01_ai_序列图

这一页是 AI 调用的序列图，以逐题评分为例。流程是：业务层先向工厂要一个 Provider，工厂返回缓存好的单例；然后业务层调用逐题评分方法；如果是真实实现，它会发起一次 HTTP 调用；结果封装成评分对象返回；最后业务层通过回调发布流式事件。上面这张图本身很直白，真正的难点在下面两个问题。第一个问题是：AI 有可能编造一道题库里根本不存在的题，用它冒充匹配结果，让 HR 以为这道题是从自己题库里挑的。我们的解法是两层结构性保证，而不是靠提示词自觉。第一层，匹配结果的返回类型只有题目编号和理由两个字段，没有题面字段——也就是说，「编造一道新题」这件事在结构上无从表达。第二层，解析时用池内编号集合做过滤，池外的一律丢弃。第二个问题是：真实 Provider 调用失败时，要不要自动降级到 Mock？我们的答案是不降级。静默降级会把规则模板的输出伪装成 AI 评估结果，既误导用户又掩盖故障。失败就返回网关错误，由用户重试——「没有」和「坏了」必须能被区分开。

# 22_模块02_interview_出题组装

第二个模块是 interview 的出题组装。目标是：从题库按岗位维度抽 N 道题，默认五道，再由 AI 按 JD 补 M 道，默认三道，合并成题目列表并写入内容快照。左边这段代码是抽取算法，用的是按维度轮询的方式，组内按编号升序，保证各个维度的题目数尽量平均。这里有一个刻意追求的性质：可预测性。相同的数据库状态下，出题结果完全确定，因此测试可以直接断言抽到了哪几道题，而不是只能断言总数量。右边第四块是差额补足公式：需要 AI 生成的数量等于 M 加上 N 减去实际抽到的题库题数，这样总题数恒为 N 加 M、也就是八道，题库不足时由 AI 补齐差额。第五块是事务边界：建面试、出题组装、把状态置为进行中，这三件事在同一个事务里，AI 出题失败就整体回滚——要么面试创建成功且题目齐备，要么什么都没发生，不留半成品。

# 23_模块02_interview_序列图

这一页是出题的序列图。从建面试的请求进来开始，业务层先读岗位与评估维度，然后向题库模块要候选池，拿回一个已按编号升序的池子，接着按轮询算法抽取，如果还缺题目就调用 AI 生成，生成结果批量落库，最后把题目写入面试并提交事务。下面两个问题是这个模块最有意思的地方。第一个问题：出题之后题目列表就写死了，没有换题接口也没有删题接口。但候选人的简历是在面试创建之后才提交的，那时才知道该考什么，怎么办？我们的解法是把「按简历补题」设计成唯一的加题例外，而且只追加、不改动既有题目。第二个问题：HR 连点几次按简历补题，会不会出一堆重复题？这里需要说清楚「幂等」的准确含义。候选池会剔除本场已有的题目编号，所以重复调用不会产生重复题目；但池子变小之后 AI 会挑下一批，所以每次调用都会再加一批题，这是有意允许的累加。因此接口会返回本次新增数量和本场总题数，界面必须显示总题数，否则连点几次会以为界面卡住了。

# 24_模块03_evaluation_三阶段

第三个模块是 evaluation 的流式评估。整个评估有三个阶段，每个阶段发一类事件：逐题评分发题目事件，多维评分发维度事件，汇总报告发报告事件。左边三张卡片描述了这三个阶段。右边是后台线程的真实源码。这里有两个设计我想特别说明。第一个是「先推后写」：结果在最后一次性落库，而且是单事务。这样数据库要么是上一次的完整结果、要么是这一次的完整结果，永远不存在混合状态；失败也不会损失既有数据。第二个是业务与传输分离：业务编排本身是同步的，流式只是传输适配。两者分开之后，业务逻辑才能脱离异步设施单独测试。底部三块补充说明：运行注册表保存在内存里，起一个守护线程并给它独立的数据库会话，因为这个会话对象不是线程安全的；注册表保留三百秒，目的是让断线重连能重放完整的事件序列。

# 25_模块03_evaluation_序列图

这一页是流式评估的完整序列图，分三段。第一段是发起：HR 点开始评估，请求进 router，调用启动运行，这一步会先丢弃上一轮的记录、再注册新的一轮、然后起一个守护线程，随即返回一个已接受状态和流式地址，前台不会被阻塞。第二段是订阅：浏览器用带认证头的请求打开流式接口，服务端在订阅的同时取事件快照、读运行状态，然后重放已推过的事件、转发新事件，终结事件之后关闭连接。第三段是后台：线程内执行业务编排，逐阶段发布事件，最后发布终结事件并安排延时回收。底部是事件契约：题目事件按序号升序推送，然后维度事件、报告事件，最后是完成或错误，这两个终结事件互斥且必居其一；另外每十五秒发一个心跳，防止代理因为空闲而断开连接。特别提醒前端的一点：流式接口需要认证头，而浏览器原生的 EventSource 无法设置自定义请求头，所以必须用 fetch 加流式读取来手动解析分帧。

# 26_模块03_evaluation_问题与解决

这一页是 evaluation 的问题清单，五个，每一个都由并发时序引起。第一个：评估跑了一半，界面永远停在半截。原因是终结事件和运行状态分两次写入，读侧可能读到「状态已终结、但终结事件还没入列」的组合，于是推出一段没有终结事件的截断流。解法是把两者放在同一把锁内写入，读侧也在同一把锁内读事件列表和状态，两边配合保证状态已终结就意味着终结事件一定在重放序列里。第二个：订阅和取快照之间的空隙会漏事件。解法是把订阅、取快照、读状态合并进同一把锁内原子完成。第三个：客户端在重放期间断开，订阅者会永久留在名单里，之后每个事件都往没人消费的队列投递，内存单调增长。解法是让异常捕获必须覆盖重放循环，在最终块里移除订阅者——如果重放不在捕获范围内，生成器在产出点收到退出信号时最终块不会执行。第四个：重新评估时，上一轮的延时回收定时器会误删新一轮的记录。解法是做身份校验，只回收仍然属于当前这一轮的记录。第五个：进程重启留下的孤儿评估。解法是以注册表作为「评估是否真的在跑」的唯一事实来源，按同一规则自愈。最后一句是给前端的：重连会从头重放，这是设计特性而不是缺陷，前端必须按题目编号覆盖，而不是来一条加一条，否则进度会翻倍。

# 27_模块04_interview_邀请并发

第四个模块是作答邀请的并发接受。左边是真实源码里的临界区。先看几个安全属性：邀请码由加密安全随机数生成，二十二个 URL 安全字符，约一百二十八位熵；一次性接受；默认七天有效；可以撤销。右上角是并发示意：同一候选人用两条不同的码，几乎同时请求接受同一场面试。解法是用面试行锁把同一场面试的接受串行化，先到者写入接受记录并返回成功，后到者拿到锁之后以当前读复查，命中已接受记录而被拒绝。右下角是四种失效原因——码不存在、已撤销、已接受、已过期——它们返回的是同一段文案，而且响应里不出现任何面试信息，否则这个公开端点就会变成邀请码探测接口。底部三张卡是三个设计决定。第一，激活是公开端点，因为拿码的人往往还没有账号，要求他先登录会让整条邀请链自相矛盾。第二，账号创建委托给 auth 模块，不在 interview 里复制用户名唯一性、密码哈希、角色约束这三条规则。第三，这个方法的签名刻意不接收当前用户参数，因为绑定到哪个账号是由请求体里的用户名决定的，与调用者身份无关。

# 28_模块04_interview_问题与解决

这一页展开讲上面那个并发问题。上面是序列图：请求 A 和请求 B 几乎同时到达，它们调用同一个接受方法，但服务端先对面试行加锁，于是两个请求被串行化，先到者写入、后到者复查命中后被拒绝。左下的问题描述是：同一候选人用两条不同的码并发接受同一场面试，如果只靠「先查后写」，并发下会双双通过，结果是候选人列表里同一场面试出现两次。解法就是用面试行锁串行化，并在锁内以当前读复查。底部三张卡回答三个「为什么」。第一，为什么必须用当前读：本事务的快照可能早于并发事务的提交，快照读读不到刚刚写入的那条接受记录，复核就会形同虚设。第二，为什么锁面试行而不是邀请行：对一条尚不存在的接受记录加锁，只会拿到间隙锁，挡不住并发；面试行才是这场绑定的真实归属。第三，为什么加锁位置放在创建账号之后：新建账号会提交事务，而提交会释放本事务已持有的锁，先加锁等于白加。

# 29_模块05_resume_上传解析

第五个模块是简历上传解析。左边是真实源码，这个端点的职责被刻意收得很窄：它是不落库、不落盘的纯转换端点——不建简历、不改简历，服务器上也不留那个文件。正因为如此，简历表的结构完全不需要变，不必新增文件路径字段。校验一共四道：第一道是扩展名白名单，只接受两种格式；第二道是文件头魔数复核，因为扩展名由客户端提供，改个名字就能绕过，所以要检查文件开头是不是真的对应那个格式；第三道是解析，文档走文档库、PDF 走 PDF 库；第四道是归一化之后的非空校验。右边是完整流程：上传、四道校验、解析、归一化、回填正文框，最后由候选人确认保存——保存走的是另外的端点，与解析这一步完全分开。底部三张卡。第一张强调不落库不落盘。第二张讲文档里的表格也必须取出来，因为简历里的教育经历、工作经历常常做成表格，只取段落会整块丢掉正文。第三张讲归一化只做四件事——统一换行、去行尾空白、折叠连续空行、去首尾空白——不做重排，因为任何更聪明的处理都会让系统偷偷改掉候选人的原文，而他看到的正文正是要被 AI 消费的内容。

---

# 30_模块05_resume_问题与解决

这一页是上传环节的四个安全问题。第一个：改了扩展名就能绕过类型检查。解法是在白名单之外再按文件头魔数复核，两道都过才解析。第二个：压缩炸弹。上传体积上限拦不住它，因为五兆的压缩包可以解出几个 G，而文档格式本质上就是一个压缩包。解法是单独设一道解压后展开体积的上限，用压缩中央目录里的原始大小求和来判断，而且不解压，所以这道检查本身几乎不吃内存。第三个：加密的 PDF 被误判为损坏。很多导出工具默认会给 PDF 加一个空密码，只看「是否加密」这个标志会误伤一批正常文件。解法是把判据收紧为「已加密、而且连空密码也解不开」，先尝试用空密码解密，成功就视为可读。第四个：扫描件 PDF 解析出空字符串。解法是归一化后为空就返回参数错误，文案点明这可能是扫描件并提示改用粘贴；旧格式文档、纯文本、图片也都在类型检查处被点名拒收，而不是走到解析才失败。底部解释了为什么这里可以写宽泛的异常捕获：两个解析库在损坏文件上抛出的异常谱系并不稳定，逐个枚举必然漏；而兜底在这里是安全的，因为本模块不落库、不落盘，宽泛捕获不会掩盖数据损坏，只会如实告诉上传方读不出来。

# 31_模块06_auth_权限守卫

第六个模块是 auth 的权限守卫与数据隔离。左边是真实的角色守卫代码，它是一个依赖工厂，返回一个可以挂到路由上的依赖。这里最关键的一条是：集合精确匹配，不做层级包含——不存在「admin 包含 hr」这类隐式规则。所以 HR 侧路由必须显式写出两个角色，候选人是单独一个；admin 不能调用候选人端接口，候选人也调不了 HR 端接口，两个方向都返回禁止访问。为什么要显式列出？因为显式是最容易评审的形式，新增角色时不会有意外的放行。另外，守卫先于请求体校验，即使请求体是空的、角色不符也仍然是禁止访问而不是参数错误。右边是三条数据隔离路径：admin 返回空、不过滤；hr 按创建者等于自己过滤；候选人按资源归属，面试则按「持有该面试的有效邀请」判定。底部结论：这套判据由测试钉住，不靠自觉。

# 32_模块06_auth_问题与解决

这一页是权限相关的四组对比，左边是错误的做法，右边是正确的做法。第一组：加入候选人角色之后，原有的 HR 侧路由只校验「已登录」，于是候选人的令牌可以直接调用 HR 接口。正确做法是把权限守卫收紧为多角色判定，HR 侧全部接口显式校验 admin 和 hr，候选人侧校验 candidate——这是本期的强制项，不是可选项。第二组：候选人的数据隔离不能复用「创建者等于自己」这个判据，因为候选人根本不是面试的创建者，那是 HR；按它过滤会让候选人看不到自己的任何面试。正确做法是新增一条独立校验路径，判据是「持有该面试的有效邀请」，不引入新机制，直接复用既有的邀请链。第三组：用户名如果已被候选人占用，直接复用账号是危险的，因为「知道对方用户名」就等价于能把他的账号绑到自己的邀请上。正确做法是必须校验密码一致才复用，不符就返回未授权；如果被 HR 或管理员占用则返回冲突。第四组：被禁用的账号能不能被复用绑定？不能。因为绑定会消耗掉一次性邀请码，而该账号此后登录和鉴权都会被拒绝，候选人永远打不开这场面试，HR 也无法重新发码——这是一条无法自行恢复的死路。底部这一句是贯穿全部六条改动的原则：把「谁有权看到什么」写成可执行的路径和判据，而不是写在注释里。

# 33_工程收获

第五部分，先说工程收获，五条。第一条，架构约束要能被测试钉住，而不是靠自觉。测试文件里直接检查「router 不得引用 repository」「service 不得出现数据库执行语句」——写在文档里的约束会腐化，写成测试的不会。第二条，让不该发生的事在结构上无从表达。匹配结果类型只有编号和理由、没有题面字段；候选人反馈是白名单模型，分数不在里面就根本没发给浏览器。靠「前端不渲染」来实现脱敏，等于把分数发出去再要求它别看。第三条，失败要显式，不要静默降级。真实模型调用失败不降级到 Mock，而是返回网关错误；判分失败不阻塞作答，标记为未判分并允许重判——「没有」和「坏了」必须可区分。第四条，先写设计契约再写实现。三十份模块计划书先定签名和字段表，再落代码；前端重建期抓到的五处「原型与真实契约对不上」，根因都是照着原型的内存模拟写字段名。第五条，测试方法本身也要能被审查。前端测试台曾经按按钮文字找「登录」，命中的却是文档顺序靠前的模式切换控件，两条断言全绿，但什么都没测到——「绿」可能只是「没测」的另一种说法。

# 34_已知局限与踩坑

这一页讲已知局限，五条，每条都标了代价或缓解手段。第一条，单进程部署是硬约束，因为流式运行注册表和刷题限流计数都在进程内，所以启动时的 workers 参数必须是 1；要支持多进程，得改用发布订阅或者任务队列加结果后端。第二条，评估和作答都不留历史版本，同一场面试只保留最近一次评估结果，HR 覆盖作答时也只保留最新内容，代价是无法回溯上一次的分数。第三条，邀请码是明文存储的，因为 HR 需要在系统内复制转达；缓解手段是长码加短有效期加一次性加可撤销，四者叠加。第四条，刷题推荐只从候选池里挑，池子上限是一百条，题库越大，排在后面的长尾题目越难被练到——这是一次有意的成本取舍。第五条，上传体积上限拦不住「服务器已经收完的请求体」，因为框架在进入视图函数之前就把请求体缓冲下来了，我们读一小段省的是自己的内存，不是服务器的；真正在请求发出前拦住大文件的是前端那道体积预检，所以这是前后端各一半的防线。底部是一条测试方法上的教训：变异检查做了三十三次，抓出五个真 bug 和六处契约偏差，其中一个是看截图看出来的——当时断言是绿的。

# 35_展望与结语

最后讲下一步规划，六项：报告分享链接、语音与视频面试及录音转写、保留简历原文件与回看原件、多候选人横向对比、后端生成 PDF 以支持脱离浏览器的批量导出、以及候选人端导出自己的脱敏反馈。它们现在都处于规划状态，没有一项进入开发。说完规划，回到这个产品本身。它和「把出题工具与刷题应用简单拼装在一起」的区别在于：简历由候选人单侧提交，却同时驱动了 HR 侧的补题和候选人侧的推荐，于是原本互不相干的两端被缝成了一个闭环。最后一句收束：AI 在其中始终扮演辅助角色，每一个 AI 产物都有人确认——HR 确认参考答案、确认准备提纲、确认最终报告。AI 负责把草稿摆到桌面上，决定权始终在人手里。谢谢各位。
